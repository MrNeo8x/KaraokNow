# Booking holds: staff API baseline

`POST /v1/merchant/booking/holds` requires a tenant membership, an authorized branch and Owner, Branch Manager or Receptionist role. `Idempotency-Key` is scoped to tenant and user; a repeated equivalent request returns the original hold, including `EXPIRED` after expiry. Reusing the key with different inputs returns 409. A new attempt requires a new key.

`GET /v1/merchant/booking/holds/{id}` returns the hold to the same permitted roles within their assigned branch and tenant. It locks the hold and expires it before returning if its TTL has elapsed, releasing the occupancy in the same transaction.

`GET /v1/merchant/branches/{branchId}/booking/holds?from=...&to=...&limit=50&offset=0` lists holds whose requested booking interval overlaps `[from,to)`, excluding the cleanup buffer from the filter. Timestamps require an explicit timezone; `limit` is 1–100 and `offset` 0–10000. The response is `{items,limit,offset,hasMore}`, ordered by booking start then ID. Overdue holds are shown as `EXPIRED` based on database time without changing stored state or releasing the room; the worker or individual GET performs expiry. Offset pagination may shift when records are inserted between requests. This endpoint lists holds and does not include confirmed bookings.

The transaction validates active room/branch and merchant duration policy, snapshots the configured channel TTL and cleanup buffer, writes occupancy as `[start, booking end + buffer)` and records audit. PostgreSQL's exclusion constraint rejects overlapping active occupancies, including maintenance. This creates a provisional staff hold; it cannot confirm a booking.

`POST /v1/merchant/booking/holds/{id}/details` attaches a required phone, optional email and a server-calculated price snapshot while the hold remains valid. Supply `expectedTotalAmountVnd` from the quote shown to the user; the server rejects a changed total with 409, and returns the already stored snapshot for an identical replay. The hold row is locked and pricing is read in the same repeatable-read transaction; expiration is checked again before writing. Customer contact is omitted from audit entries and branch hold lists. Existing holds without details remain provisional.

After making a successful manual phone call, authorized staff can record the result using `POST /v1/merchant/booking/holds/{id}/phone-verification`. The active hold must already contain a phone number. The first request records the database timestamp, staff user and audit event; concurrent or repeated requests return the first result without duplicate audit. An expired hold is rejected. This records a staff assertion and does not perform a phone call or confirm a booking.

`POST /v1/merchant/booking/holds/{id}/confirm` accepts exact nonempty cancellation terms and confirms only a verified, unexpired hold with a contact and price snapshot when the channel deposit mode is NONE and the merchant has explicitly enabled no-deposit confirmation for that channel. It locks the hold, serializes policy reads against policy updates, snapshots policy versions and copies customer, price, verification and terms into a booking; hold and occupancy become CONFIRMED atomically. Repeating the same request returns the same booking, different terms cause 409. `GET /v1/merchant/booking/bookings/{id}` reads it under tenant and branch authorization. Channel configuration alone is supported; case-level eligibility, deposit-required booking, transitions after confirmation, public booking and manual payments remain unimplemented. PostgreSQL E2E covers concurrent confirmation replay and an expiry/confirmation lock scenario; broader stress testing remains pending.

Run `npm run holds:expire` from `be/` as a supervised separate process. The worker uses PostgreSQL row locks and `SKIP LOCKED`, atomically changes expired holds to EXPIRED, releases occupancy and records audit. It retries failed batches with exponential backoff capped at 30 seconds, writes redacted error/recovery events and drains the active batch before shutdown on SIGINT/SIGTERM. `GET /v1/merchant/booking/hold-expiry/backlog` lets an Owner see the number of overdue HELD records and oldest overdue age for their tenant without changing them; the endpoint is not a worker heartbeat. Until the worker runs, an expired hold can continue to block search/new holds; a replay or individual GET also expires its own hold when due. PostgreSQL Docker E2E starts the worker as a child process, verifies expiry and graceful SIGTERM locally. Production supervision, alert thresholds and recovery after a real infrastructure outage are not verified. A future confirmation transition must lock the same hold row and check `expires_at` against database time before changing state.
